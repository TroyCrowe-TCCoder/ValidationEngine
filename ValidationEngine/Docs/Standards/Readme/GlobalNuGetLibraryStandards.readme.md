# GlobalNuGetLibraryStandards.md — Rationale and Context

This file documents the rationale, history, and decision context for rules in [`GlobalNuGetLibraryStandards.md`](../GlobalNuGetLibraryStandards.md). Per [`GlobalFileSpecificationStandards.md` Section 2.16](../GlobalFileSpecificationStandards.md#216-readme-companion-file), this content must not appear in the standard itself.

## v1.3.0 — Analyzer-package-family exception (nuget-library.2.2, nuget-library.3.2)

The one-repository-per-library and matching-names rules exist to keep a shared library's identity unambiguous: one repo, one solution, one package, all sharing a name. That assumption breaks down for Roslyn analyzer packages, which are deliberately small and numerous — the `ToolingRoutingMatrix.md` decomposition of the standards corpus produced roughly a dozen natural analyzer packages (one per standards domain: Coding, Caching, Logging, Security, Testing, and so on). Requiring a dedicated Azure DevOps repository for each of those would multiply repository-onboarding overhead (branch policies, pipeline wiring, `.github/copilot-instructions.md`, marker exclusions) by a factor of ten-plus for packages that are otherwise identical in shape, lifecycle, and ownership.

The exception treats a repository like `GlobalStandards.Analyzers` as a *family* rather than a single library: one repository, onboarded once, hosting several sibling packages that are versioned and published independently of one another. What's relaxed is only the repository-per-package cardinality, because the packages are close cousins (same audience, same publishing pipeline shape, same review/governance model) rather than unrelated libraries that happen to share a home.

This exception is intentionally narrow: it requires the repository to be *explicitly designated* as an analyzer-package family, so it cannot be invoked informally to justify bundling unrelated shared libraries (e.g., `HttpClientManager` and `DataImportExportManager`) into one repository for convenience. Naming still enforces traceability — each package is `<RepositoryName>.<Domain>` — so package identity remains unambiguous even though the repository hosts more than one package.

## v1.4.0 — Single repository-root solution for analyzer-package families (nuget-library.2.2, nuget-library.3.2)

v1.3.0 initially required each domain package within an analyzer-package-family repository to have its own dedicated `.slnx`, reasoning that solution-level isolation would prevent accidental cross-domain coupling. On review, that isolation benefit doesn't hold up: packaging (`dotnet pack`), versioning, and CI triggering all operate at the project (`.csproj`) level, not the solution level, so a project reference between two domains is exactly as easy (or hard) to introduce in a single shared solution as in separate ones. Meanwhile, one `.slnx` per domain (potentially 6-8+ solutions in one repository) requires a brand-new "multi-solution repository" CI pattern that doesn't exist anywhere else in the standards corpus — every other governed repository pattern assumes exactly one `.slnx` — and adds real day-to-day overhead (opening/building/testing across several solutions) for no corresponding benefit.

The rule now requires a single repository-root solution (named after the repository, e.g. `GlobalStandards.Analyzers.slnx`) containing every domain's analyzer project and test project. This reuses the existing single-solution shared-library pipeline pattern with per-project pack/publish steps instead of requiring a new multi-solution pattern, while fully preserving independent packaging and versioning per domain — the only things that actually matter for consumers.
